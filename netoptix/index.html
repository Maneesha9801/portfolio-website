The Problem

Network Engineering often feels stuck in a terminal-first world. At Ribbon Communications, I commonly faced a critical invisibility problem: routing protocols when configured without traffic engineering blindly prefer the 'Shortest Path' metric, often flooding a single link while alternative, higher-cost paths sit idle. When such issues were raised, diagnosing this congestion was a very exhausting process. It required SSH-ing into dozens of disjointed nodes, parsing thousands of lines of monochrome CLI logs, and manually correlating asynchronous timestamps to understand what was going on in the network. Essentially, I was forced to mentally render a complex, dynamic topology inside my head because the tools offered no visual spatial awareness.

The Friction

  • ⚠High Cognitive Load: Engineers must memorize IP addresses and cable connections.
  • ⚠Slow Diagnosis: Spotting a single "dropped packet" line in a 5,000-line log takes minutes.
  • ⚠Lack of Context: Text logs show status, but they don't show flow.

The Design Challenge

How might we transform network debugging from a task of reading and memorizing into a task of seeing and reacting?

Backend Engineering: Data Ingestion

The Challenge: Network devices output unstructured, raw text. To visualize it, I needed to convert thousands of lines of legacy CLI output into structured JSON data in real-time.

The Solution: I leveraged Perl for its superior text-processing speed and regular expression (Regex) capabilities—standard for legacy network automation.

How it works:

  1. Ingestion: The script SSHs into the node, or parses compressed .zstf log files and captures live streams (e.g., show isis neighbors detail).
  2. Regex Extraction: I wrote custom Regex patterns to scrape key data points: Neighbor IDs, Interface Metrics, and Link States directly from the raw ASCII stream.
  3. State Machine Logic: The script maintains a 'state' of the network, maintaining 'flapping' links before sending the clean JSON object to the frontend.

I designed this tool as a translation layer between machine protocols and human perception. The goal was to shift the user's cognitive mode from "Reading & Memorizing" (System 2 thinking) to "Seeing & Reacting" (System 1 thinking).

Intervention A: Logic-First Topology (The Overview)

The UX Decision: Physical maps create noise. I designed a Logical Topology that spatially groups nodes by their routing hierarchy (ISIS Level 1 Aggregation vs. Level 2 Core).

The Engineering: I utilized Flex Algorithms to color-code paths based on intent (e.g., Green = Low Latency, Blue = IGP Metric), allowing engineers to distinguish "Core Traffic" from "Edge Traffic" instantly.

The Outcome: Instant architectural awareness. The user understands the network's behavior, not just its wiring.

Flex Algorithm Color Coding

Intervention B: Visualizing Stress (The Feedback)

The UX Decision: I replaced static lines with Biomimetic Interfaces. Healthy links are thin and stable; congested links physically thicken and pulse, mimicking inflammation in a biological system.

The Engineering: I implemented a physics-based congestion engine where Utilization > 100% triggers a "Stress Animation" and visually slows packet velocity to represent latency.

The Outcome: Pre-attentive processing. The user spots the bottleneck in <200ms—before they even read the data.

Intervention C: Contextual Reconstruction (The Details)

The UX Decision: Raw CLI configs are overwhelming but necessary for validation. Instead of dumping static logs, I built a "Just-in-Time" information architecture.

The Engineering: I built a parser that dynamically reconstructs the specific router configuration and CLI commands (e.g., set protocols isis...) based on the node's active role, accessible via a context menu.

The Outcome: The full power of the terminal is preserved but scoped. Visual noise is reduced by 90%, keeping the canvas clean for decision-making.
